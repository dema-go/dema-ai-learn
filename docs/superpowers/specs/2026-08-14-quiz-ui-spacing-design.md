# 「考我一下」答题交互与全局间距优化设计规范

> 日期：2026-08-14  
> 状态：待用户复核  
> 设计范围：微信原生小程序 P0+P1 已有页面的 UI 优化  
> 依据：`AGENTS.md`、`UI原型图.md`、`需求分析.md`、既有正式 UI 规范及本轮用户确认结果

## 1. 目标

本轮优化解决两个已在现有小程序中出现的直接体验问题：

1. 相邻按钮距离过近，视觉上融合为同一个控件，主次关系不清楚。
2. 答题选项可用宽度偏窄；提交答案后，反馈和下一步落在首屏下方，用户需要继续向下滚动。

优化后的答题主路径为：

```text
阅读题目
  → 点击接近满屏宽度的选项
  → 立即提交并判题
  → 在原选项上看到勾或叉
  → 就地阅读解释或查看原文依据
  → 点击固定底部的下一题
```

本轮不改变材料输入、题目生成、记录、隐私等产品范围，不新增题型、积分体系或社交能力。

## 2. 已确认的设计决策

### 2.1 答题提交方式

- 点击选项后立即提交，不再要求用户点击“确定答案”。
- 提交期间锁定全部选项，避免快速点击导致重复请求。
- 判题前不显示可点击的确认按钮；底部操作区只提示“点选答案后立即判题”。
- 判题完成后，底部操作区切换为“下一题”；最后一题切换为“查看结果”。

### 2.2 正确状态

- 正确选项直接显示绿色边框和浅绿色背景。
- 选项前置标记由字母切换为绿色圆形勾。
- 同时出现“回答正确”文字，确保正误状态不只依赖颜色。

### 2.3 错误状态

- 用户错选项显示红色边框、浅红色背景和红色圆形叉。
- 正确选项同时显示绿色边框、浅绿色背景和绿色圆形勾，并标注“正确答案”。
- 同时出现“这次选错了”文字，不使用羞辱或惩罚性表达。
- 其他未选择的错误选项保持中性样式。

### 2.4 解释与原文依据

- 解释统一放在完整选项组下方，不嵌入某一个选项内部，避免展开后推动后续选项并改变位置。
- 解释使用紧凑信息块，不再使用占据较大纵向空间的独立反馈卡。
- “查看原文依据”紧跟解释区域，作为次级操作。
- 答错时不强制展开完整原文抽屉；默认显示简短解释和清晰入口，减少首屏占用。
- 原文依据仍必须展示后端返回的最短直接支持片段，不得使用材料外知识补充。

## 3. 答题页布局

### 3.1 页面骨架

答题页从上到下分为四个稳定区域：

1. 顶部状态区：题目进度、进度条、题型和“这题有问题”。
2. 题目区：题干。
3. 作答与反馈区：选项、即时判题结果、解释和原文依据。
4. 固定底部操作区：判题提示、下一题或查看结果。

当前页面重复出现的题型标签应合并为一个，避免浪费首屏空间。

### 3.2 横向尺寸

- 页面左右安全边距统一为 `16px`。
- 选项占满安全边距之间的全部可用宽度。
- 选项不得额外套入会继续缩窄内容区的卡片容器。
- 固定底部操作区与页面使用相同的 `16px` 左右边距。

### 3.3 选项尺寸

- 选项最小高度为 `56px`。
- 选项内部水平内边距为 `14–16px`，垂直内边距不小于 `12px`。
- 选项之间保持 `12px` 间距。
- 选项标记拥有固定宽度，不因 A、B、C、D 或勾叉切换造成文本跳动。
- 长选项允许自然换行，不截断关键内容，也不降低可点击高度。

### 3.4 固定底部操作区

- 操作区固定在页面底部并适配微信安全区。
- 内容滚动区增加与操作区实际高度对应的底部留白，任何解释或原文依据不得被遮挡。
- 判题完成前，操作区展示不可点击的提示文案。
- 判题完成后，只展示一个满宽主按钮。
- 常规 2–4 选项题应尽量在首屏完成“选择—反馈—下一题”；长题干、长选项或长解释仍允许正文区域滚动。

## 4. 交互状态与数据流

### 4.1 状态机

```text
idle 未作答
  → 用户点击选项
submitting 提交中
  → 接口成功
answered 已判题
  → 下一题
idle 未作答
```

异常路径：

```text
submitting 提交中
  → 接口失败
idle 未作答 + 明确重试提示
```

### 4.2 提交中

- 点击后立即记录当前选择并进入 `submitting`。
- 被选项显示中性选中态和轻量加载标识，但不提前出现红绿结果。
- 所有选项暂时禁用，同一题同一时刻只允许一个提交请求。
- 底部提示保持不可点击，不能在结果返回前进入下一题。

### 4.3 提交成功

- 正误、正确选项、解释和原文依据以答题接口响应为准。
- 前端使用响应中的 `is_correct` 和 `correct_index` 渲染状态，不根据题目对象中的答案字段自行判定。
- 保存接口返回的 `attempt_id`，继续沿用现有作答链路。
- 若返回本关结果，继续写入现有 `last_result`，不改变结果页数据协议。

### 4.4 提交失败

- 不显示正确答案、解释或原文依据。
- 解除选项锁定并回到可作答状态。
- 提示“提交失败，请重新选择”；网络错误可附带现有接口返回的具体原因。
- 用户可以再次点击任意选项重试。
- 若后端返回“该题已经答过”，前端不得伪造本地判题结果；实施阶段应复用或补充现有恢复机制，重新取得服务端认可的作答进度。

## 5. 全局按钮与间距系统

本轮选用“均衡”密度，兼顾按钮边界和移动端纵向空间。

| 场景 | 间距或尺寸 |
| --- | --- |
| 页面左右安全边距 | `16px` |
| 同组纵向按钮间距 | `12px` |
| 并排按钮间距 | `12px` |
| 主操作与次操作组间距 | `16–20px` |
| 普通卡片之间 | `16px` |
| 不同内容区块之间 | `24–32px` |
| 主按钮最小高度 | `48px` |
| 答题选项最小高度 | `56px` |

### 5.1 按钮排列规则

- 主按钮默认占满可用宽度。
- 只有同等级且文案较短的两个操作可以并排，并排时各占可用宽度的一半。
- 存在明显主次关系时使用纵向排列，不用相同颜色和尺寸制造虚假的同等级关系。
- 相邻按钮不得依赖阴影区分；按钮之间必须存在真实空白。
- 页面只保留一个视觉主行动。
- 删除重复入口。例如无错题结果页只显示一次“再考一篇”，不得同时作为主按钮和次级按钮出现。

### 5.2 全局巡检页面

实施阶段必须检查以下已有页面：

- 首页与输入方式选择；
- 文本输入与网页输入；
- 生成等待与生成预览；
- 逐题答题与即时反馈；
- 通关结果与错题复测完成；
- 最近记录、记录详情与错题本；
- 免费额度、隐私与删除确认；
- 帮助反馈和个人页。

固定底部操作栏主要用于答题、复测等连续任务页面。普通列表、记录和设置页面仍随内容自然排列，不统一强制吸底。

## 6. 组件边界

实施时应将本轮规则收敛为少量清晰组件或公共样式：

- `choice-card`：负责未选、提交中、正确、错误和正确答案五种视觉状态。
- `answer-feedback`：负责结果文字、解释和原文依据入口。
- `bottom-action`：负责安全区、判题前提示、下一题和查看结果。
- `button-stack` / `button-row`：负责全局按钮组间距，不允许页面通过零散 margin 拼接。

各组件只负责自身布局与状态表达；页面控制当前题目、接口请求和跳转。

## 7. 可访问性与动效

- 正确和错误必须同时使用颜色、边框、图标和文字。
- 勾叉图标需要提供可读标签，不能只作为装饰图。
- 选项禁用时仍需保持文字可读，不使用过低透明度。
- 提交中只使用轻量旋转或脉冲反馈；开启 `prefers-reduced-motion` 时取消循环位移动效。
- 固定底部按钮应满足微信安全区并保持不低于 `48px` 的触控高度。
- 长文本换行后，选项内部标记与首行文字顶部对齐，避免视觉漂移。

## 8. 验收标准

### 8.1 功能状态

- 点击一个选项立即发起一次提交，无“确定答案”步骤。
- 连续快速点击不会产生多个并行提交。
- 答对时仅正确选项显示绿色勾和明确文字。
- 答错时错选项显示红叉，正确选项同步显示绿色勾。
- 提交失败不会提前展示答案，并可重新选择重试。
- 下一题和最后一题的结果跳转保持现有业务行为。

### 8.2 视觉与布局

- 在 `320px`、`375px` 和 `390px` 视口宽度下无横向溢出。
- 选项在页面 `16px` 安全边距内占满宽度。
- 2、3、4 个选项以及长题干、长选项、长解释均可正常显示。
- 固定底部操作区不遮挡选项、解释或原文依据。
- 页面按钮符合统一间距规则，不再出现边框或阴影粘连。
- 无错题结果页不存在重复“再考一篇”。

### 8.3 验证方式

- 对状态转换和快速点击保护增加前端可执行测试；若当前小程序测试基础不足，至少将状态判断抽成可测试函数。
- 运行现有后端测试，确认答题接口契约未被破坏。
- 在微信开发者工具模拟器中完成完整作答与错题复测流程。
- 人工模拟网络失败，验证重试行为。
- 使用不同长度的真实中文题干和选项检查可读性与触控区域。

## 9. 范围之外

本轮不重新设计品牌角色、首页信息架构、导航结构、题目生成流程或结果统计模型；不增加题型、计时竞争、动画奖励、分享能力或后端数据字段。若实施中发现即时提交需要新的服务端恢复接口，应作为保障当前交互可靠性的最小配套改动单独列入实施计划，不扩展为新的作答系统。
